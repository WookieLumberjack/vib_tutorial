# vib_tutorial

Real-time teaching app for an N-mass spring-damper chain (PySide6 + pyqtgraph + NumPy/SciPy), managed with uv.

- Run: `uv run vib-tutorial`. Test: `uv run pytest` (GUI smoke test runs headless via `QT_QPA_PLATFORM=offscreen`).
- `src/vib_tutorial/core/` is NumPy/SciPy with no Qt imports; keep it that way so it stays testable and scriptable.
- Rust kernels live in `native/` (PyO3, abi3), built by maturin (the package's build backend) into `vib_tutorial._native`; `uv sync`/`uv run` rebuild it when the Rust changes. Each kernel replaces a Python function that stays as the reference: `core/native.py`'s `kernel(name, reference)` picks the Rust one when it's built, `VIB_NATIVE=0` runs the Python everywhere, and `tests/test_native.py` compares the two. Name the Python `<name>_reference` and keep the public name for the dispatch (`fluid_bearing.pi_film`). The release builds' `--smoke-test` fails if the module didn't load.
- `src/vib_tutorial/gui/` holds the Qt widgets. `main_window.py` owns the timer loop and wires the panels to `Simulator`.
- Units are SI throughout (kg, N/m, N·s/m, m, N, Hz in UI / rad/s internally where named `omega`).
- The simulator uses an exact FOH matrix-exponential discretization. Don't replace it with an explicit integrator, because stiff user inputs must stay stable.
- `core/measurement.py` (virtual modal test) uses the same FOH update, diagonalized into one `lfilter` per eigenvalue (`ChainResponse`) so long records are fast; it steps directly when the eigenvectors are singular. With friction it steps through `Simulator.drive` instead (~1–7 µs a step in Rust, 20–90 in the Python), so `Acquisition.work(budget)` measures in slices and the page calls it each frame; keep new acquisition code resumable (`yield from` the analog runs).
- Friction's steps (`Simulator.start`, `drive`) run in Rust (`native.FrictionSteps`, one per input kind from `_friction_kernel`, cached in `_friction_cache`), mirroring `_advance_friction_reference`/`_drive_reference` and `_friction_step` event for event, each sub-step's map from `expm_balanced`. Its energy ledger differs in method only: the input's work from an integrator state q = ∫x_k, and the dampers' loss from the energy balance (exactly 0 without dampers), instead of Van Loan's integrals, so an event costs one exponential, not three. The force is open-loop, so `start` works out every step's force first (`_forces`). Keep the two in step; `tests/test_native.py` compares them.
- The Rust kernels release the GIL while they step. `Simulator.advance` is `start` then `collect`: with friction (`steps_aside`), `start` moves the force and the clock, hands the Rust steps to a worker thread and returns; `collect` waits for them and finishes the ledger. Anything that touches `state` (`set_state`, `set_system`, …) waits for them first, and `reset` drops them. The Simulation page starts them as a frame ends, so they run while it paints, and records them at the next frame (`_collect`; it doesn't wait if they aren't done); a system change records them first, under the system they ran with. Without friction the steps hold the GIL, so the page steps them inline and draws them in the same frame. The rotor page steps inline too: its film kernel is ~1 ms of an ~8 ms frame at 1× (drawing is most of it), not worth the threading yet.
- `core/back_expansion.py` recovers the interior DOFs from the coupled CMS solution; its enhanced recovery adds the interior states to the reduced model's state vector (`RecoveryResponse`), so it shares the same exact FOH step.
- `core/modal_coupling.py` (Modal coupling page) reduces each side of a split to one oscillator per chosen mode. With A's tip modal mass and B's residual mass (the defaults) the 2-DOF model is exactly the Rayleigh–Ritz projection of the chain, and a test checks this. Keep it so, because the page's upper-bound notes depend on it.
- `core/rotor_sweep.py` (rotor page's Bode and polar plots) tracks the 1X vector once per revolution, keyed to the unbalance angle φ, from every simulator step (not the page's decimated history). `RunUpCoastDown.advance` stops each simulator advance at the next stage change, so the legs start and end at the set speeds. The page clears held sweeps when the rotor's parameters change, since the steady-state curve under them changes too.
- `core/fluid_bearing.py` (the rotor page's *Fluid-film bearing* tab) is a plain journal bearing by short-bearing (Ocvirk) theory: equilibrium and the eight coefficients in closed form, in the rotor's axes (x horizontal, y up, load down, spin x → y), with `film_force` by quadrature to check them (tests compare the two). On the rotor (`Bearing.film`, both bearings, the tab's geometry) each film carries `RotorSystem.bearing_loads` (its share of the weight, from statics on the model's own stiffness; the film's own `load` is ignored), is held at ε = 0.9 below `slowest()`, and is linearized about its journal's equilibrium: `_film_terms` gives K_f, C_f and the constant load p = W + K_f q_J, which `gravity_load(Ω)` adds so the journals rest on the locus. The simulator holds p at each chunk's speed, as A(Ω).
- With `nonlinear_films` the simulator steps the films' whole force instead (`whole_films`: on a round shaft; a turning shaft keeps them linear). `pi_film` gives it in closed form with its stiffness, damping and dissipation Ψ (tests check it against `film_force` and finite differences). `RotorSimulator._film_steps` keeps the exact FOH update, with each film's K_f and p but its damping replaced by the bound C_b (`full_film_damping`, the uncavitated film's, taken afresh as the journal moves), and adds the remainder as a load on the journals, found each step by Newton (`_Films.solve`, cut back on the convex Q). Don't put C_f back in the update: near the wall the remainder would be stiffer than the update, the step rings, and the journal is thrown through the wall. The Rust kernel (`native.FilmSteps`, one per held speed and step from `_Films.stepper`) runs `_film_steps_reference`'s loop and takes the bound itself as the journals drift, with its own FOH exponential (`linalg.rs`'s `expm_foh`: Al-Mohy–Higham on the augmented matrix's blocks, balanced first, since A h runs from h to K/M h; more accurate than SciPy's here). ~1.6 µs a step, ~6 µs on Oil whirl, where the journals circle near the wall and the bound is retaken every ~15 steps (the Python: 45–120 µs). Keep the Rust in step with `_film_steps_reference` and `_Films`; `tests/test_native.py` compares them while ramping and through retakes, and the FOH with `foh_discretize`. The step only resolves the spin and the modes coarsely (`FILM_MODE_STEPS`), and the page caps each frame's computing (`step(…, budget)`). Everything else (Campbell, stability, steady states) stays linearized.
- `core/magnetic_bearing.py` (the rotor page's *Magnetic bearing* tab) is an active magnetic bearing: a magnet pair per axis (negative stiffness k_m, current gain k_i, from the gap, bias, pole area and turns) under a PID with a filtered derivative behind a first-order amplifier, `gain(s)` in closed form and `state_space()` per axis (tests check they agree). On the rotor (`Bearing.magnet`) its -k_m is in K and the controllers' states follow q and q' in the state: size states from `system.n_states` (2 n_dof + `n_control`), take velocities as `state[n:2n]`, not `state[n:]`. The steady states add the magnets' k_i G(ikΩ) at each harmonic (`support_stiffness`, `dynamic_solve`); with integral action the 0X row pins the journals at the centre, and the rest state comes from `static_state` (A z + B f = 0). Their slow integrator roots are near-repeated and split by a hair, so `whirl_modes` counts a root with |Im λ| < `OVERDAMPED` |Re λ| as not oscillating, and reports the fastest such growth as `drift` (a magnet too weak for k_m diverges without oscillating); `least_damped` and `growth_rate` use it.
- A stator ring round the disc (`RotorSystem.stator`, a `Stator`; the *Rub* tab, `gui/rotor_rub.py`) is in the time response only: `stator_force` gives the ring's push and smoothed-Coulomb drag with its derivatives, and `RotorSimulator._rub_steps` adds it to the exact FOH update as a load on the disc, linear over the step, solved by Newton (`_rub_solve`), as the films' remainder is. The Rust kernel (`native.RubSteps`, built per call from the chunk's Φ, Γ0, Γ1) runs `_rub_steps_reference`'s loop, `stator_force` and the heat included: ~0.6 µs a step against 10–60 in the Python; keep them in step (`tests/test_native.py` compares them). `step_size` resolves the disc on the ring's mount. Only on a round shaft with the films linearized (`__post_init__` raises; the page drops the ring and disables its checkbox). Campbell, stability and the steady states leave it out. Each advance's `RotorSamples.rub` holds the push; the page's history keeps the largest since the last sample kept (`PUSH`). A forward full rub's steady state is a linear one with the ring as a cross-coupled spring at the disc; a test checks it. With `thermal_gain` the rub's heat (column 3 of `rub`) bows the shaft (Newkirk): `RotorSimulator.thermal_bow`, complex from the mark, held over chunks of at most τ/`THERMAL_STEPS` and moved on by `_warm` (exact first-order lag), loads the shaft as the residual bow does (`bow_load`, in `force`). The page records the spiral (`_record_spiral`) at a steady speed only.
- The rotor's stiffness depends on speed: K + ΩH, with H from the shaft's internal damping and the bearings' fluid swirl (`Bearing.swirl`, k_xy growing as λcΩ) (`RotorSystem.circulatory()`, `speed_dependent`), plus an oil film's K_f(Ω); its damping too, C + C_f(Ω). K itself is not symmetric once a bearing has cross-coupling (`kxy`, `kyx`). Use `system.stiffness(omega)` and `system.damping(omega)` wherever the speed is known, not `matrices()` alone (it leaves the films out). `core/rotor_stability.py` finds the onset speed by sweeping and bisecting the least damped mode's ζ.
- The disc may sit between the bearings or overhang one (`position` > 1 or < 0, never on a bearing). The shaft's nodes come from `RotorSystem._mesh` in axial order, and the 3D view spans `system.extent`, so don't assume the disc is between 0 and L. Presets live in `core/rotor_presets.py`, and `tests/test_rotor_presets.py` checks the numbers in their notes.
- The shaft may have mass (`density` > 0): it is then a beam FE model (`elements`, consistent or `lumped` mass), reduced Craig–Bampton style to the stations plus the shaft's fixed-interface modes up to `MODE_LIMIT` (`RotorSystem._reduced`). So q is `[the 8 station DOFs, ξ_x, ξ_y]`: `XA`…`YB` keep their indices, but q has `system.n_dof` entries. Size arrays from `n_dof` (not 8 or `N_DOF`), split or build the planes with `plane_dofs`/`merge`/`plane_load`, and get the shaft's shape anywhere from `deflection`. M is then full (`mass_inverse`). With density 0 the model is exactly the massless Jeffcott one whatever `elements` is (a test checks); keep it so. Raising `MODE_LIMIT` costs time: the time step resolves the fastest mode kept.
- Everything that turns with the rotor (unbalance, balance weights, disc skew, shaft bow) goes through `RotorSystem.rotating_load(Ω, Ω')`, as f_x + i f_y = P e^{iφ} on [A, D, θ, B]; both the simulator's `force` and `synchronous_response` use it, so the steady state and the time response can't drift apart. A new 1X source belongs there. Two-plane balancing's `plane_weights` (`PlaneWeight`) go there too: on the disc they add to `mass_unbalance` and `couple_unbalance` (a weight at axial offset h adds w·h to the couple); on the shaft each is a point force S(z)ᵀw. The Balancing tab keeps its readings at all four stations, and forgets its trial runs when the planes change, since the influence matrix belongs to them. φ is the keyphasor mark's angle, not the heavy spot's: every rotor angle (unbalance, weights, bow, skew) is measured from the mark, and the heavy spot drawn is `mass_unbalance`'s.
- An asymmetric shaft (`asymmetry` Δ, EI(1 ± Δ), stiff axis at `asymmetry_angle` from the mark) has a stiffness that turns with it: `stiffness(Ω)` is its mean, `stiffness_at(Ω, φ)` the whole thing at an instant. Its modes are Floquet modes (`_rotating_modes`, exact in axes turning with the shaft, on isotropic supports; `_hill_modes` otherwise), its steady states come by harmonic balance (`harmonic_response`: `synchronous_response`'s 1X, `gravity_response`'s mean sag and 2X), and the simulator splits each step around a mid-step kick from the turning part (exact FOH with K held when it stands still). Its criticals are its two axis rotors' (`axis_system`), and `Onset.end` is where its unstable band ends. A round shaft takes none of these paths; tests check that Δ → 0 matches it.
- A cracked shaft (`crack`, a `Crack`) is a hinge at the crack (compliance from `crack_compliance`, by depth), condensed exactly onto the stations (`_hinge_loss`). Breathing, the weight opens it (`crack_sign`, `crack_open(φ)`), so its stiffness has 1X, 2X and 3X; held open it turns with the shaft like the asymmetric one. Both are one Fourier series, `_periodic_terms` (the crack's mean goes in K, the harmonics E_k turn): test `system.periodic`, not `asymmetry`, for anything that turns; `spacing` is 1 for a breathing crack (harmonic balance then couples every harmonic, Hill's method steps by Ω) and `rotating_frame` says when the rotating-frame modes are exact. `steady_harmonics` gives the whole steady state (gravity and 1X loads together, 1X–3X), which the Bode plot and the tracker (`vectors3`) compare. A massless shaft's crack does not depend on `elements` (a test checks).
- Gravity (`RotorSystem.gravity`) only moves the rotor's equilibrium to `static_deflection(Ω)`. Anything that measures vibration (the 1X tracker, peaks, the spectrum, the phase readout) works on `vibration(system, q, Ω)` (`core/rotor_sweep.py`), the motion about it; only the drawing can show the sag (the page's *Static sag* box). On an asymmetric shaft gravity also drives 2X: the sag is then the mean of a periodic motion, and the 2X stays in the vibration.
- The rotor page's right pane is `TabGroups` (`gui/tab_groups.py`): five group tabs, each with its own row of tabs (ten in one row didn't fit). Reach a view with `tabs.show_page(widget)` and `tabs.current_page()`, not `setCurrentWidget`/`currentWidget`: they work across the groups and see through the `ColumnScroll` round the Balancing and bearing panels. Those panels draw only while their tab shows: a change while hidden marks them `_stale` (`tucked_away`, which checks the tabs above them too: a panel that's its group's current tab isn't `isHidden()` while another group shows), and they draw on `showEvent` or `catch_up()` (the page calls it on a tab switch, since a window never shown gets no show events). They're still built with the page, so the right pane keeps their minimum widths. What they keep as state (the bearing panel's load box, the balancing buttons) stays outside the deferred part; a test that reads their drawing shows the tab first.
- The window fits a 1280 px screen (`test_window_fits_a_1280_px_screen`; 1159 offscreen): it's as wide as its widest page, and a page as its splitter's panes' minimums together. So don't put a long row of controls in a QHBoxLayout (its minimum is the sum of theirs): use `gui/layouts.py`'s `FlowLayout`, which wraps, with `group(...)` keeping a label with its control. Parameter panes and tall panels are `ColumnScroll`s (up and down only, as narrow as their contents allow; give their plots `plot_height`, or they scroll where the plots could have shrunk). A combo box with long items gets `AdjustToMinimumContentsLengthWithIcon`. Check a layout change with the window at 1280×800, not just 1700×900.
- Anything that drives the rotor simulator over several frames (run-up, balancing measurement) is a `StagedRun` (`core/rotor_sweep.py`): resumable `advance(duration)`, each simulator advance stopped at the next stage change. The page runs at most one at a time; taking over the speed or changing a parameter cancels it.
- The rotor page's *Waterfall* tab (`core/rotor_waterfall.py`) is fed the page's stored history samples (every stride-th step, as the vibration about the sag) at all four stations, so changing the station needs no new data. Each block records the free whirl frequencies of the rotor it was measured on, so a new rotor, speed range or block length starts it afresh (`_new_waterfall`). Every line is filled (hidden lines), so it's redrawn at most every `WATERFALL_FRAMES` frames.
- The strip chart (`TimeHistoryPlot`) decimates incrementally: `Decimator` caches each curve's own min/max per bucket (a bucket per pixel column of the plot, so the line covers the pixels the whole record would) by absolute sample number (`History.offset`), and `update_data` gets a `values(index)` callback so only new and decimated rows are derived. If the plotted values of samples already seen change (other curves, a new modal map), go through `set_curves`, which resets the cache.
- The Simulation page's history keeps every stride-th step (`_store_stride`: samples STORE_DT apart, or STORE_PER_PERIOD to the fastest mode's or forcing's period, `Simulator.fastest_hz`, or a tenth of a pulse), continuing the stride across advances (`_carry`). The presets keep every step; a stiff chain's 7.6 µs steps keep every 4th, so the 300,000 samples span ~9 s, not 2.3. Everything recorded per sample (energies, element forces) is worked out only for the kept ones; the energy balance still closes on them.
- `Simulator.advance` caps the number of steps per call (`MAX_STEPS_PER_ADVANCE`). Loop over it for long runs in tests. The Simulation page also caps each frame's steps to its compute budget (`FRAME_BUDGET` over the measured cost of a step, `PROBE_STEPS` while a new system's isn't known), so a test that wants a set stretch of simulated time from `_tick` should call `sim.advance` itself.
- The rotor page's analysis (Campbell, stability onset, steady states: `core/rotor_analysis.py`'s `analyse`, 0.2–6 s) runs in `AnalysisWorker`, a spawned process shared by the pages (`gui/rotor.py`'s `WORKER`), 150 ms after the parameters settle; `_poll_analysis` shows it, and a change while a job has run over `RESTART_S` restarts the worker rather than wait. Not a thread: the frames hold the GIL and would starve it. What it sends and returns must pickle, and `analyse` must not touch Qt. Tests and scripts can still call `_refresh_analysis()`, which works it out at once. The worker hides the parent's `__main__` while it spawns (so unguarded scripts aren't rerun); `vib_tutorial.main` calls `freeze_support()` for the packaged app, and `--smoke-test` checks the worker answers.
- BLAS runs on one thread (`vib_tutorial.main` sets `OPENBLAS_NUM_THREADS` and friends before NumPy loads, and the worker always): the matrices are small, and OpenBLAS's pool made the cracked shaft's frames 6× slower. Measure before letting BLAS thread again.
- `gui/frame_stats.py` is the frame-timing overlay (`VIB_FRAME_STATS=1`, or a CSV path to log too). Every page's frame loop runs inside `frame_stats.frame(page, sim_t, target_ms)` (free when it's off), and `MainWindow.event` times each repaint; wrap a new frame loop the same way, start its next frame `FRAME_MS` after this one began (not after it ended: that adds the frame's work to every interval), and end it with `gui.settle_plots(page)` (it applies the plots' new ranges in the frame: pyqtgraph defers them to the paint, which then dirties the items and paints every rescaling plot twice). Don't touch a plot's items in a frame where nothing on it changed (the Bode marker at a steady speed): any change repaints its axes and grid. The CSV also has `view` rows (what shows: the tabs picked, a page's `frame_context()`, window size, scale, Hz) and `input` rows (`InputLog`, an app-wide event filter: the control's label and new value); `scripts/frame_report.py` cuts a log at them and summarizes each stretch. Give a new page a `frame_context()` if what it shows isn't in its tabs (the rotor's preset).
- Colours come from the theme in `gui/style.py`, read at draw time through `colors` (`colors.mass[i]`, `colors.force`, `colors.muted`). Don't hard-code a colour: it has to be legible in every theme (`style.contrast` gives the WCAG ratio; aim for 3:1 for curves, 4.5:1 for text). A widget that keeps pens or brushes across redraws needs an `apply_theme()`, called from `MainWindow._restyle`. Mute secondary labels with `theming.mute`, not a stylesheet colour.
- To check UI changes, grab a screenshot offscreen: run the script with `QT_QPA_PLATFORM=offscreen` (only the tests set it; without it the window opens on the real display and gets resized by the compositor). Create the app with `gui.make_app("Light")` (or another theme name); `gui.run()` uses the theme last picked, which is stored in the user's settings. This sets Qt's palette and pyqtgraph's background (the default is black). Then build `MainWindow`, resize it to 1700×900 (the README screenshots' size), run the event loop briefly, and `window.grab().save(path)`. Check a change in Light and Dark at least; `MainWindow.set_theme(name)` switches live. The README images come from `scripts/readme_screenshots.py`; rerun it (or just the affected shots) after a visible UI change and check the captions' numbers still hold.
- Releases: pushing a `v*` tag that matches `pyproject.toml`'s version runs `.github/workflows/release.yml`, which builds unsigned PyInstaller apps (`packaging/vib-tutorial.spec`) on Linux, Windows and macOS, launches each with `--smoke-test`, and publishes them as a GitHub Release. Build locally with `uv run --group build pyinstaller packaging/vib-tutorial.spec`. If a new feature imports a Qt module, check the spec's `EXCLUDES` and `DROP` lists don't remove it. To try the builds on a branch, `gh workflow run release.yml --ref <branch>` (merges only build when they touch the packaging or dependencies).
- pyqtgraph views left in a scene until interpreter exit can segfault in PySide's teardown (exit 139 *after* pytest prints "passed"). `gui.close_graphics(widget)` tears them down; `gui.run()` and the GUI tests' autouse fixture call it. Check the exit code, not just the summary line.
- Don't let Qt delete a layout item behind PySide's back (e.g. `setParent(None)` on a widget in a layout, which `PlotWidget.close()` does). PySide wraps the items of a filled layout added to another, never learns of the deletion, and a new QObject at the reused address then resolves to the stale wrapper: intermittent segfaults, seen on macOS in `QMenu.addAction`. Take the item out with `layout.takeAt()` first, as `close_graphics` does.
